IMPLEMENTATION AND LIMITS
set_exception_handler validates nullable callbacks before changing state and
returns the previous original callable value. get_exception_handler preserves
that identity; restore_exception_handler pops null entries too and returns true.
Dispatch retains the old handler on its stack, clears the active handler, and
resolves the stored callable again in the request-boundary scope. Referenced
callback-array members remain live. A handler can explicitly install a new
handler to process its exception; ordinary handler throws do not call themselves
again. When no handler remains after invocation, the stack supplies restoration.
Internal handler argument diagnostics use Unknown:0 and internal trace frames.
Invalid callbacks after scope unwinding produce PHP's fatal callback diagnostic.

File/stdin execution enables handlers after entry compilation succeeds. CLI -r
and initial compilation failures bypass them; nested eval/include exceptions
retain the enclosing execution boundary. Runtime::report_uncaught dispatches
handlers; execution APIs still return errors for callers to report. Successful
handling sets exit status 0; explicit exit and unhandled handler exceptions retain
native statuses. Existing default Throwable rendering remains the fallback.

Related failures still need shutdown callbacks, destructor behavior, error
handlers, output buffering, deprecation attributes, or closure-debug metadata.
No full shutdown lifecycle or PHP compatibility claim is made. PHP 8.5.0
Zend/zend_builtin_functions.c, Zend/zend.c, Zend/zend_execute_API.c, native
signatures, upstream fixtures, and reference execution establish behavior.
Adapted handler rules retain Zend license attribution.
